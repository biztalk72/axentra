# FORGE AX 제품 요구사항 정의서

버전 1.0 · 2026-11-03 · 상태: MVP 구현 / 파일럿 설계

## 1. 제품 정의

FORGE AX는 데이터 연결 → 가상화 → 시뮬레이션 → 분석·판단 → 승인·실행 → 피드백을 하나의 운영 공간에서 연결하는 제조 AX 플랫폼이다. 초기 고객은 생산라인 1~5개를 운영하는 중소·중견 이산 제조기업으로 가정한다. 첫 파일럿은 정밀 가공·조립 공정으로 한정한다.

UVC의 OCTOPUS 공개 발표에서 확인한 8개 기능 영역을 비교 기준으로 사용했다. 구현 기술, 알고리즘, 성능, 내부 아키텍처를 복제하거나 동등성을 주장하지 않는다. FORGE AX는 독립적으로 작성한 MVP이며 UVC와 제휴 관계가 없다.

- [UVC OCTOPUS 소개](https://uvc.co.kr/octopus): 제품의 공개 기능 영역.
- [UVC 2026-02-12 제품 발표](https://uvc.co.kr/pr/news/99): Edge, Data Hub, Twin, Simulator, AI Hub, Agentic AI, Robot Hub, Physical AI의 8개 구성과 순환 구조. 열람: 2026-11-03.

## 2. 해결할 문제와 사용자

설비 데이터가 PLC·MES·ERP에 분산되고, 현장 담당자는 알람을 발견한 뒤 별도 도구로 원인을 찾고 작업을 지시한다. 공정 변경은 경험에 의존하며, AI 분석은 실제 운영 작업과 연결되지 않는다.

| 사용자 | 핵심 업무 | 제품에서 얻는 결과 |
|---|---|---|
| 공장장 / 생산 관리자 | 생산 현황, 라인 이상, 승인 | 한 화면에서 우선순위와 실행 결과 파악 |
| 현장 운영자 | 데이터 수집, 작업지시, 운반 작업 | 설비 맥락을 유지한 업무 처리 |
| 공정 엔지니어 | 병목 분석, 조건 비교 | 기준 대비 변경 시나리오 기록 |
| 데이터 분석가 | 이벤트 탐색, 모델 실험 | 재현 가능한 데이터와 모델 버전 |
| 플랫폼 관리자 | 계정 권한, 연결 관리, 감사 | 통제 가능한 실행·배포 이력 |

운영 시나리오: CNC 온도 상승 → 이벤트 표준화·저장 → 설비 맵에서 이상 확인 → 통계 모델의 현재값 판정 확인 → 공정 변경 시나리오 비교 → 냉각 점검 제안 승인 → 점검 작업 생성 및 가상 AMR 운반 → 감사 이력 확인. 시뮬레이션 결과는 운영자가 참고하며 점검 제안의 자동 근거로 사용하지 않는다.

## 3. 제품 목표와 측정

다음 목표는 파일럿에서 검증할 제안치다. MVP에서 달성한 성능 수치가 아니다.

| 지표 | 파일럿 제안 목표 | 측정 방법 |
|---|---|---|
| 이상 발견 후 담당자 확인 시간 | 기존 대비 30% 단축 | 이벤트 시각 ~ 확인 시각 중앙값 |
| 설비 데이터 수집 성공률 | 일일 99% 이상 | 유효 이벤트 수 / 송신 이벤트 수 |
| 시나리오 검토 소요시간 | 표준 조건 5분 이내 | 실험 생성 ~ 결과 검토 |
| 작업 제안 추적성 | 승인 작업 100% 감사 기록 | 제안·승인·작업·사용자 연결 검사 |
| 중복 수집에 따른 수량 왜곡 | 동일 source/event_id 0건 | 재전송 테스트와 유일키 검사 |

OEE는 계획시간·실가동시간·이상 사이클·총 생산수를 확보한 뒤 제공한다. 현재 화면의 **설비 운영 지수 = 가동/주의 설비 비율 × 누적 양품률**이며 OEE가 아니다. 대시보드의 누적 양품은 전체 설비 처리 수량이다. 완제품 실적은 A라인 QC, B라인 Packaging 공정에서만 MES 작업지시에 반영한다.

공통 기능: MES 기본 작업지시, 세션 인증, admin/operator/viewer RBAC, 자가 가입(operator 고정), 감사로그, OpenAPI, health check, Prometheus metrics, Alembic, Docker Compose.

명시적 비범위: 실제 PLC 제어, 완전 자율제조, 안전 PLC 기능 대체, 인증받은 안전 제어, 기업별 ERP/BOM/재고/LOT 업무, 현장 성능 보장, 학습된 로봇 정책, 임의 자율 도구 실행. 선택적 Ollama 연계는 구현했으며 실제 모델 서비스는 미연결이다. 전체 플랫폼은 위 후속 범위를 단계별로 완성한다.

## 6. 사용자 경험

기본 구조: 고정 네이비 사이드바 + 밝은 작업 공간 + 상단 맥락·검색 + 작업별 페이지. 주요 색은 cobalt blue(주요 실행), teal(정상), amber(주의), muted gray(설정/대기)다. 색상만으로 상태를 전달하지 않고 텍스트와 점을 함께 사용한다.

대시보드: 4개 핵심 지표 → 설비 디지털 맵 / AX 인사이트 → 생산 추이 / 라인 현황 → 전주기 바로가기. 급한 업무를 먼저 파악하고 상세 분석으로 이동하게 한다. 증거 없는 추세 상승률·성과 숫자·AI 정확도를 꾸미지 않는다.

모바일: 아이콘 내비게이션, KPI 2열, 분석 패널 1열, 표 내부 가로 스크롤. 모달은 키보드 포커스 순환·Escape 종료·배경 클릭 종료를 지원한다. 운영자·조회자는 할 수 없는 작업 버튼을 비활성화하고 서버에서도 다시 검사한다.

## 7. 데이터와 계산 계약

- 설비: 고유 ID, 종류, 라인, 상태, 주기, 최신 온도/진동, 누적 양품/불량.
- 이벤트: source + event_id 유일키, 설비 FK, UTC timestamp, 온도[-50,250], 진동[0,100], 양품/불량[0,10000].
- 업무 리소스: connector/order/robot/alert/recommendation/simulation/model/job/dataset/maintenance 범주와 상태·JSON 파라미터. MVP의 메타데이터 확장용이며 규모 확장 시 전용 테이블로 분리한다.
- 세션: opaque bearer, DB에 token hash와 만료시각 저장. 브라우저는 sessionStorage를 사용한다. 서버 연결 모드의 실제 권한은 DB 사용자에서 조회한다.
- 감사: actor, action, target, detail, UTC created_at. 현재 DB 관리자에 대한 변조 방지는 보장하지 않는다. 파일럿은 WORM 저장·외부 수집 추가.
- 시뮬레이션: baseline = floor(hours×3600 / max(cycle) × 0.90 × 0.98). 변경값은 cycle×(1-reduction), 가동비(1-downtime), 양품비(1-defect)로 계산. 모든 설비가 직렬 단계라는 단순 가정이며 discrete-event 엔진이 아니다.

## 8. 기업형 시스템 구성

초기는 모듈러 모놀리스로 운영 복잡도를 제한한다. React/TypeScript, Nginx, Python/FastAPI, SQLAlchemy, PostgreSQL을 핵심 경로로 사용한다. Redis와 Mosquitto는 integration profile의 선택 인프라이고 애플리케이션 경로에는 연결하지 않았다. S3 호환 저장, Keycloak/Entra ID, MLflow, 메시지 버스는 확장 설계다.

자세한 구조와 실제/계획 상태는 [아키텍처](ARCHITECTURE.md)를 따른다.

## 9. 신뢰성·보안·운영 요구사항

파일럿 목표(미측정): UI 읽기 p95 500ms, 500건 수집 p95 2초, 8시간 이상 연속 수집, 단일 사업장 내 99.5% 가용성. 부하 검증 전 생산 SLA로 사용하지 않는다.

MVP는 단일 사업장·소규모 운전용이다. SQLite는 빠른 로컬 체험용이고 병렬 트랜잭션 검증은 PostgreSQL에서 수행한다. 설비·작업 잠금과 조건부 갱신으로 중복 실행을 막고, 수집 유일키 충돌은 409로 재시도를 요청한다. 다중 API 인스턴스에서는 가상 스트림을 하나의 수집 워커로 분리해야 한다.

생산 전 필수 전환: TLS, 관리형 secret, OIDC/MFA, 로그인 rate limit, tenant/plant 분리, 감사 외부 보존, DB 백업·복구 훈련, 데이터 보존·파티셔닝, 관측/알림, 프로토콜 자격증명·네트워크 분리. 실장비 제어는 별도의 위험 검토·인터록·승인·현장 검증이 필요하다.

## 10. 출시 단계와 의존성

| 단계 | 범위 | 종료 조건 |
|---|---|---|
| MVP — 현재 | 8개 영역의 축소 수직 흐름 + MES + 관리자 + Pages 체험 | 기능 테스트·빌드, 실행 가이드, PRD, 체험 링크 |
| 파일럿 — 제안 4~6주 | 1개 현장, REST/OPC-UA 수집, ERP 작업지시, SSO, 운영 관측 | 실제 데이터 검증·재전송·권한·복구 테스트, 사용자 서명 |
| 제품화 — 제안 8~12주 | 다사업장·시계열·MLflow·비동기 워커·3D | 용량 및 보안 목표 측정, 회귀 테스트, 운영 인수 |
| 자율운영 — 별도 산정 | 로봇 어댑터·LLM/MCP·물리 엔진·정책 학습 | 현장 제어 계약·안전 검증·정책 게이트 통과 |

기간은 필요한 데이터·인력·현장 접근을 확보한 경우의 계획 가정이다. 파일럿 전에 업종, 설비 인터페이스, ERP, 통신망, 생산 지표 정의, 이벤트 빈도, 사용자 수, 보존 기간을 확정한다.

## 11. 검증·릴리스 기준

- 백엔드 통합: 인증/로그아웃, 권한, 수집 멱등·지연·원자성, 이상 제안, 승인/반려, 시뮬레이션/데이터셋, 모델 배포, 로봇 상태, 완제품 집계, 라인 중복, 감사·CSV.
- Pages 체험: 동일 업무 흐름을 브라우저 저장소로 검증. 서버 인증·권한·동시성의 증거로 사용하지 않는다.
- 빌드: TypeScript 검사 + Vite 배포 빌드. lockfile을 저장하고 CI에서 재현한다.
- 운영: PostgreSQL migration → bootstrap → API health → Nginx. 주요 컴포넌트 재시작 후 데이터 보존 확인.
- UI: 실제 Chrome에서 서버 연결 대시보드와 주요 흐름, 모바일 레이아웃을 점검한다.

검증의 실제 수행 상태는 [검증 기록](VERIFICATION.md)에 남긴다.

## 12. 계정 흐름 개정

관리자 이메일을 admin@admin.com으로 통일하고 자동 관리자 진입을 제거했다. 암호 원문은 공개 저장소에 두지 않는다. 방문자는 직접 체험 계정을 만들며 operator로 입장한다. 가입 비활성화, 세션 만료·로그아웃, 재로그인, 관리자 전용 작업 제한과 사용자 목록을 지원한다. 공개 Pages의 계정은 브라우저 단위이고 실제 서버 계정과 별개다. 세부 사항과 제한은 [계정 가이드](ACCOUNTS.md)를 따른다.

## 13. 현장 및 멀티 에이전트 개정

현장 화면은 오피스 콘솔과 분리된 `/#panel/{id}` 전체 화면으로 제공한다. 참조 `UI-sample/`의 대형 지표·설비 카드·터치 타일을 반영했다. [현장 패널 운영](FIELD-PANELS.md), [CCTV 설정](CCTV.md)에 구성·게시·장치 설치 계약을 정의한다.

멀티 에이전트는 ARTEX의 제어 구조를 제조 진단용으로 독립 구현했다. 카메라를 자산 그래프에 포함하되 영상 분석 AI를 구현한 것으로 표시하지 않는다. [멀티 에이전트 설계](MULTI-AGENT.md)에 역할·실행 상태·도구 모드와 선택적 LLM 연계 범위를 정의한다.
